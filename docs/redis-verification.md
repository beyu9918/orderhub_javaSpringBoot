新增检查包含：

- 同一个不存在商品连续查询五次，商品 Mapper 只查一次，空值 key 的 TTL 在 60–75 秒范围内；创建商品后空值失效。
- 24 个并发请求通过两个独立缓存对象访问同一冷 key，数据库加载回调仅执行一次；锁结束后清理。
- 正常 TTL 随机范围为 30–35 分钟；过期持有者不能发布旧数据或释放后继锁；锁忙等待超时不绕回数据库。
- 32 个 Lua 请求争抢 5 个名额，恰有 5 个预扣成功；重复预扣不替换原令牌。
- 两个独立 Redisson 客户端对同一用户并发领取，返回同一张用户券；不同用户竞争时 PostgreSQL 与 Redis 余额一致，无超发。
- 在数据库增加领取计数后强制插入失败，计数及用户券一起回滚；Redis 预扣补偿后可再次成功领取。
- Redisson 不可用时数据库领取仍可成功并保持幂等；之后重建 Redis，不重复发券。
- 中断预扣恢复时跳过仍持锁的请求；没有数据库记录则释放名额，有记录则只确认、不重复加库存。
- 旧令牌 / generation 不能补偿新代次；管理员修改后的 epoch 阻止旧快照回填。

另在 `orderhub-v1-verify` 隔离 Compose 环境中，以已验证的 JAR 和本地 Java 21 镜像构建并运行，通过真实 HTTP 验证：领取、同用户重试、不同用户售罄 409、pending 清理、商品空值缓存。短暂停止该隔离 Redis 后，领取成功落入 PostgreSQL；恢复 Redis 后服务正常。

仅更新隔离服务 `http://localhost:18080`，未更新现有 `8080` 应用，根目录 `.env` 未修改。验证过程中新增的测试账号与优惠券保留在隔离演示库，正式业务库未被清理。PostgreSQL 集成测试使用 orderhub_v1_test，测试缓存使用 Redis DB 1。

本次是功能与并发正确性验证，不是吞吐压测，也没有据此宣称 QPS 或性能提升百分比。
